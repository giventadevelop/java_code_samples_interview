1. Should a Map key be mutable?

Short answer: Map keys should be immutable (or treated as immutable after insertion). Mutable keys are allowed by the language, but they are dangerous and usually the wrong design.

What “mutable key” means

A key is mutable if fields used by equals() / hashCode() can change after the object is put into a HashMap, HashSet, or similar hash-based collection. Classic risky examples: a custom class with setters on id/name, or using an ArrayList / array as a key and then modifying it.

Why mutability breaks HashMap

HashMap places an entry in a bucket based on key.hashCode() at insert time. Later lookups use hashCode() again, then equals(), to find the same bucket and entry.

If you change the key’s state after insert:

  1. Its hashCode() may change → map looks in a different bucket.
  2. The entry is still sitting in the old bucket.
  3. Result: get(key) returns null, containsKey is false, and the entry becomes effectively lost (a “ghost” entry) until iteration/removal by identity of the old object.
class MutableKey {
    int id;
    MutableKey(int id) { this.id = id; }
    public int hashCode() { return id; }
    public boolean equals(Object o) {
        return o instanceof MutableKey mk && mk.id == id;
    }
}

Map<MutableKey, String> map = new HashMap<>();
MutableKey key = new MutableKey(1);
map.put(key, "A");

key.id = 99;                 // mutated after insert
System.out.println(map.get(key)); // null — lost!

Advantages of immutable keys

AdvantageWhy it matters
Stable hash location Entry remains findable for the life of the map
Correct equals/hashCode contract Lookup, replace, and remove behave predictably
Thread-safety of key identity Other threads cannot change “which key” an entry is
Simpler reasoning Key is a value identity, like a primary key in a database
Safe use in HashSet / as map keys in caches Same hashing rules apply to sets

When would someone use a mutable object as a key?

  • Almost never as a hash key.
  • Acceptable only if you never mutate fields that affect equals/hashCode while the object is in the map (effectively treating it as immutable).
  • IdentityHashMap uses reference identity, so field mutation does not move the key — but that is a special-purpose map, not a general recommendation.
  • TreeMap with a Comparator that ignores mutable fields can be less fragile, but mutable sort keys are still a design smell.
Best practice: prefer String, boxed primitives, records, or other immutable types as keys. If you must use a custom class, make key fields final and do not expose setters that change equality state.

2. Effectively final variables — what, why, advantages

Definition: A local variable or parameter is effectively final when its value is never changed after initialization, even if it is not declared with the final keyword.

What it means in practice

int x = 10;          // effectively final — never reassigned
Runnable r = () -> System.out.println(x);  // OK

int y = 10;
y = 11;              // reassigned → NOT effectively final
Runnable bad = () -> System.out.println(y); // compile error

Java requires that local variables captured by lambdas, anonymous classes, or local classes be final or effectively final.

Why Java requires this

  • Lambdas/anonymous classes may run later, on another thread, or after the enclosing method returns.
  • Local variables live on the stack frame of the method. When the method ends, that stack frame is gone — so the lambda cannot literally “share” the stack slot.
  • Instead, Java copies the value into the lambda/closure instance.
  • If the original local variable could still change, the copy and the original would diverge — confusing and error-prone. Forcing immutability of the captured binding avoids that inconsistency.
Important nuance: “Effectively final” applies to the variable binding, not deep object immutability. You may mutate fields of an object the variable refers to: list.add("a") is fine if list itself is never reassigned.

Advantages of effectively final (and why you should prefer it)

AdvantageExplanation
Enables lambdas / streams / callbacks Required to compile when a local is used inside a lambda or anonymous class
Clearer intent Readers know this value is a stable snapshot for nested code
Fewer accidental bugs Stops “I changed the local later but the lambda still sees the old copy”
Safer concurrent reads of the captured value The captured copy does not race with later assignments to the local
Matches final semantics without ceremony You get the safety of final without always writing the keyword

When should a variable be effectively final?

  • Must: whenever it is referenced from a lambda, anonymous class, or local class.
  • Should: for most locals that represent a single computed value (ids, configs, results) — reassignment often signals the variable is doing too many jobs.
  • If you need a mutable counter/flag across a lambda, use an atomic (AtomicInteger), an array of size 1, or redesign with streams/collectors instead of fighting the rule.
// Good: effectively final capture
String name = user.getName();
users.forEach(u -> System.out.println(name + " saw " + u));

// If you need mutation visible across calls, don't capture a changing local:
AtomicInteger count = new AtomicInteger();
list.forEach(item -> count.incrementAndGet());

3. Checked exceptions — advantages and disadvantages

What are checked exceptions?

In Java, exceptions under Throwable split into:

  • Unchecked: RuntimeException and Error (and their subclasses). Compiler does not force you to catch or declare them.
  • Checked: all other Exception subclasses (for example IOException, SQLException, InterruptedException). The compiler requires that a method either:
    • handle them with try/catch, or
    • declare them with throws.
Design intent: checked exceptions represent recoverable, expected failure modes that callers should consciously handle (file missing, network down, parse failure), as opposed to programming bugs (NullPointerException, IllegalArgumentException). 
// Checked: must handle or declare
public String readFile(Path path) throws IOException {
    return Files.readString(path);
}

// Unchecked: compiler does not force handling
public int parseId(String raw) {
    return Integer.parseInt(raw); // may throw NumberFormatException
}

Advantages of checked exceptions

AdvantageDetail
Compile-time forcing function Callers cannot silently ignore known failure modes
Self-documenting API throws IOException is part of the method contract
Encourages recovery paths Prompts retry, fallback, user message, or cleanup in finally/try-with-resources
Clear separation from bugs Distinguishes “environment/IO went wrong” from “programmer mistake”
Safer refactoring of IO-heavy code Adding a checked throw updates call sites that must adapt

Disadvantages of checked exceptions

DisadvantageDetail
Verbosity / boilerplate Lots of try/catch or throws cascading up the stack
Leaky abstractions Low-level SQLException/IOException may surface through business APIs
Awkward with lambdas / streams Functional interfaces usually cannot throw checked exceptions cleanly
Swallowing temptation Developers write empty catch blocks just to satisfy the compiler
Interface rigidity Changing checked throws breaks binary/source compatibility of interfaces
Not loved by all ecosystems Many modern libraries prefer unchecked exceptions or Result types

Practical guidance

  • Use checked exceptions for recoverable, caller-relevant failures at API boundaries where handling is realistic.
  • Prefer unchecked exceptions for programming errors and for deep internal layers where every method declaring throws becomes noise.
  • At module boundaries, wrap low-level checked exceptions in a domain exception (checked or unchecked) so callers do not depend on JDBC/IO types.
  • Never empty-catch a checked exception “to make it compile.” Log, translate, or rethrow deliberately.
// Wrap low-level checked exception at a boundary
public User loadUser(String id) {
    try {
        return repository.find(id);
    } catch (SQLException e) {
        throw new DataAccessException("Failed to load user " + id, e);
    }
}

4. Generics: upper vs lower bounded wildcards (PECS)

In Java generics, upper bounded wildcards restrict an unknown type to a specific type or its subclasses (? extends T), while lower bounded wildcards restrict it to a specific type or its superclasses (? super T).

Core differences

Feature Upper bounded wildcard Lower bounded wildcard
Syntax <? extends T> <? super T>
Meaning Any type that is T or a subclass of T Any type that is T or a superclass of T
Main purpose Reading data from a structure Writing data into a structure
Design principle Producer Extends (PE) Consumer Super (CS)

Upper bounded wildcards (? extends T)

An upper bounded wildcard relaxes the restrictions on a variable by limiting the unknown type to be a specific type or a subclass of that type.

Usage scenario: use this when you want to read items from a collection, but you do not need to add anything to it. Java guarantees that whatever comes out will be at least of type T. 

import java.util.List;

public class UpperBoundExample {
    // Accepts a List of Number or any of its subclasses (Integer, Double, etc.)
    public static double sumOfList(List<? extends Number> list) {
        double sum = 0.0;
        for (Number n : list) {
            sum += n.doubleValue(); // Safe to read as Number
        }
        return sum;
    }
}
Note: you cannot add items (except null) to a List<? extends T> because the compiler cannot guarantee which specific subclass the list actually holds (it might be List<Integer> or List<Double>).

Lower bounded wildcards (? super T)

A lower bounded wildcard limits the unknown type to be a specific type or a superclass (parent) of that type.

Usage scenario: use this when you want to write (add) items into a collection. Java guarantees that the collection can safely hold objects of type T (and typically its subclasses as well, via polymorphism). 

import java.util.List;

public class LowerBoundExample {
    // Accepts a List of Integer or any of its superclasses (Number, Object)
    public static void addIntegers(List<? super Integer> list) {
        list.add(1); // Safe to write Integer
        list.add(2);
    }
}
Note: when reading from a List<? super T>, returned items are typed as Object because the compiler cannot guarantee which specific superclass is being used.

The PECS rule

To remember when to use which wildcard, use the PECS mnemonic:

  • Producer Extends: if your collection produces data (you only read from it), use <? extends T>.
  • Consumer Super: if your collection consumes data (you only write to it), use <? super T>.
Interview one-liner: copy(src, dest) is often declared roughly as copy(List<? extends T> src, List<? super T> dest) — read from a producer (extends), write to a consumer (super). 
public static <T> void copy(List<? extends T> src, List<? super T> dest) {
    for (T item : src) {
        dest.add(item);
    }
}

5. Fixing isTrue(Boolean) — syntax, logic, and null safety

Question: What is wrong with this method, and how do you fix it? 
public boolean isTrue(Boolean input) {
    if( !input.equals(Boolean.FALSE){   // broken
        return true;
    } else {
        return false;
    }
}

Sample code for this topic lives in com.boot2.booleancheck.BooleanIsTrueFix.

Plain-English explanation of the bugs

The method is supposed to answer a simple question: “Is this value true?” It takes a boxed Boolean (which can be true, false, or null) and should return a primitive boolean (true or false only).

1) Syntax / line-level error (will not compile)

The if is missing a closing parenthesis before the opening brace: 

if (!input.equals(Boolean.FALSE){     // wrong
if (!input.equals(Boolean.FALSE)) {   // correct

Until that parenthesis is fixed, Java will not compile the class at all.

2) Logical / runtime error — null crashes the method

Even after fixing the parenthesis, this line is unsafe: 

input.equals(Boolean.FALSE)

That calls a method on input. If someone passes null, there is no object to call equals on, so you get a NullPointerException. A method that promises to return boolean should not blow up on a missing value.

3) Logical confusion — “not false” is not the same as “is true”

The broken code asks: “Is this value not false?” That is different from “Is this value true?”

  • For Boolean.TRUE and Boolean.FALSE, the answers happen to line up.
  • For null, “not false” is philosophically fuzzy — and if you tried a null-safe version of “not equals false,” null could be treated as true. Usually, “is true?” should answer false when the value is missing.

4) Style / clarity problem

Writing if (...) return true; else return false; is longer than needed. The condition itself already is the answer. Prefer returning the boolean expression directly.

Correct solution (plain English)

Ask the constant whether it equals the input: Boolean.TRUE.equals(input). You never call a method on a possibly-null input, so null is safe and returns false. Only an actual Boolean.TRUE returns true. 
public boolean isTrue(Boolean input) {
    // Call equals on the constant, not on input → null-safe
    return Boolean.TRUE.equals(input);
}

Expected results

Input Correct isTrue Broken version
Boolean.TRUE true true (after syntax fix)
Boolean.FALSE false false (after syntax fix)
null false NullPointerException
Interview one-liner: Never call equals on a possibly-null boxed value. Use Boolean.TRUE.equals(input) so null is safe and only true means true.

6. BeanFactory vs ApplicationContext (Spring / Spring Boot)

Question: What is the difference between a BeanFactory and an ApplicationContext in Spring Boot?
Short answer: BeanFactory is the basic IoC container (get beans / wire dependencies). ApplicationContext extends BeanFactory and adds enterprise features: events, i18n, AOP integration, resource loading, Environment, and eager singleton startup. In Spring Boot you almost always work with an ApplicationContext (for example SpringApplication.run(...)).

What is BeanFactory?

org.springframework.beans.factory.BeanFactory is the root interface for accessing the Spring bean container. It knows how to:

  • Instantiate beans
  • Wire dependencies (DI)
  • Look up beans by name/type (getBean(...))

Classic implementations include DefaultListableBeanFactory / XmlBeanFactory (legacy). A plain BeanFactory is often described as lazy: singleton beans are typically created when first requested (unless configured otherwise).

What is ApplicationContext?

org.springframework.context.ApplicationContext is a sub-interface of BeanFactory. Everything BeanFactory can do, ApplicationContext can do — plus application-level services.

Common Spring Boot types: AnnotationConfigApplicationContext, AnnotationConfigServletWebServerApplicationContext, GenericWebApplicationContext, etc. Boot’s SpringApplication.run returns an ConfigurableApplicationContext.

Core differences

Feature BeanFactory ApplicationContext
Role Basic IoC / DI container Full application container (IoC + extras)
Inheritance Root bean container interface Extends BeanFactory (and other interfaces)
Bean creation (typical) More lazy — create on first getBean Eagerly instantiates singleton beans at startup (fail-fast)
Internationalization (i18n) Not built-in MessageSource support
Event publishing No Yes — ApplicationEventPublisher / @EventListener
AOP / proxies Possible but limited convenience Integrated AOP (transactions, security proxies, etc.)
Resource access Basic ResourceLoader / ResourcePatternResolver (classpath*, file:, etc.)
Environment / profiles Limited Environment, @Profile, property sources
Auto-registration of beans Manual / lower-level Post-processors, component scan, Boot auto-config
Spring Boot usage Rarely used directly by app code Default — what Boot starts and injects

Spring Boot angle

  • You do not normally create a raw BeanFactory in a Boot app.
  • @SpringBootApplication + SpringApplication.run builds an ApplicationContext, runs auto-configuration, and registers beans.
  • Inject ApplicationContext (or specific collaborators) if you need programmatic lookups/events — prefer constructor injection of your own beans first.
  • Internally, every ApplicationContext still uses a BeanFactory underneath (often accessible via getBeanFactory() on configurable contexts).
@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        // Returns ApplicationContext (which IS-A BeanFactory)
        var ctx = SpringApplication.run(DemoApplication.class, args);
        MyService service = ctx.getBean(MyService.class);
    }
}

When would you talk about BeanFactory in an interview?

  • To show you know ApplicationContext is a richer container built on BeanFactory.
  • Memory-sensitive or special low-level tooling might use BeanFactory alone (uncommon in modern Boot apps).
  • Understanding startup: ApplicationContext eager singletons catch config errors early; BeanFactory laziness can defer cost/errors until first use.
Interview one-liner: BeanFactory = basic DI container; ApplicationContext = BeanFactory + events, i18n, resources, Environment, AOP integration, and eager singleton startup — what Spring Boot actually runs.

7. Quick comparison summary

Topic Rule of thumb Main payoff
Map keys Keep keys immutable after insert Lookups keep working; no lost entries
Effectively final Do not reassign locals captured by lambdas Safe, consistent closures; required by compiler
Checked exceptions Use for expected recoverable failures; avoid ceremony spam Forced handling vs. verbosity / lambda friction
Generics wildcards PECS: producer extends, consumer super Safe read/write APIs without over-constraining callers
isTrue(Boolean) Use Boolean.TRUE.equals(input) Null-safe; true only when value is actually true
BeanFactory vs ApplicationContext Use ApplicationContext (Boot default); BeanFactory is the core DI SPI Events, i18n, AOP, Environment, fail-fast startup
Interview one-liners:
  • Mutable map key: changing hashCode/equals state after put loses the entry.
  • Effectively final: assigned once; required so lambdas capture a stable copy of the local.
  • Checked exception: compiler-enforced recoverable failure; great for contracts, costly in boilerplate and streams.
  • PECS: ? extends T to read (producer); ? super T to write (consumer).
  • Boolean check: Boolean.TRUE.equals(input) — never call equals on a null boxed Boolean.
  • BeanFactory vs ApplicationContext: ApplicationContext extends BeanFactory with app services; Spring Boot runs an ApplicationContext.
