Concurrency & JVM

Given a multi-threaded Java application that occasionally exhibits deadlocks under heavy load, describe your systematic approach to identify, analyze, and resolve the deadlock, and how you would prevent similar issues in future development.
JavaDeadlockConcurrency
Answer (brief):
  • Detect: Reproduce under load; capture thread dump (jstack, jcmd Thread.print, VisualVM) when hung; look for “Found one Java-level deadlock”.
  • Analyze: Map lock order from stacks (who holds A waiting for B). Confirm circular wait vs long GC / pool starvation.
  • Resolve: Enforce global lock ordering; shrink critical sections; prefer tryLock(timeout) / interruptible locks; redesign to single lock or lock-free structures where safe.
  • Prevent: Static analysis / reviews for nested locks; avoid lock-in-callback; use higher-level concurrency (ConcurrentHashMap, actors/queues); chaos tests that assert no deadlock under load.

You need to integrate a legacy Java module that uses synchronized collections with a new high-concurrency service. What issues might arise, and how would you design a solution that balances thread safety with maximum performance?
ConcurrencyCollections
Answer (brief):
  • Issues: Coarse Collections.synchronized* locks serialize throughput; compound operations (check-then-act) are not atomic; mixing with concurrent collections can hide races; legacy APIs may hold locks while calling out.
  • Design: Isolate legacy behind a façade; copy-on-boundary or queue async writes into the legacy module so hot path stays on ConcurrentHashMap / lock-free structures.
  • Balance: Keep synchronized collections only where mutation volume is low; for hot paths migrate to concurrent collections + explicit atomic APIs; use read replicas / immutable snapshots for readers.

A cloud-based analytics platform is experiencing memory bloat and slower batch job completion times. How would you identify the memory issues, and what strategies would you use to optimize memory usage and batch job performance?
JVMMemoryBatch
Answer (brief):
  • Identify: Heap dumps + histogram (jmap, Eclipse MAT, async-profiler); GC logs (-Xlog:gc*); container RSS vs heap; look for retained caches, large lists, classloader leaks.
  • Memory: Stream/chunk instead of loading full datasets; bound caches (Caffeine/size+TTL); off-heap/columnar formats; fix leaks (thread locals, static maps).
  • Batch speed: Right-size parallelism vs GC; partition work; push filters early; tune GC (G1/ZGC) and container limits; avoid thrashing from oversubscription.

Security & transactions

You need to ensure secure API-to-API communication between Spring Boot microservices using Spring Cloud in a zero-trust environment. How would you architect authentication and authorization, and what Spring Cloud features would you leverage?
Spring CloudZero TrustSecurity
Answer (brief):
  • AuthN: mTLS between services (service mesh or Spring Cloud Gateway + certs) plus short-lived OAuth2/JWT (client credentials) from IdP (Keycloak/Cognito/Entra).
  • AuthZ: Scopes/roles in JWT; fine-grained checks via Spring Security method security; optionally OPA/policy sidecar. Never trust network location alone. (plain-English detail)
  • Spring Cloud: Gateway as policy enforcement point; Spring Cloud LoadBalancer; config via Config Server/Bus for rotating keys; Resilience4j circuit breakers; optional Spring Authorization Server for internal tokens.
  • Zero-trust extras: Deny by default, least privilege, continuous verification, audit logs, secrets in vault—not in images.

JWT, scopes, and AuthZ in plain English

AuthN vs AuthZ (do not mix them up)

Plain EnglishExample question
AuthN (authentication) “Who are you?” — prove identity. Is this really service order-api / user Alice?
AuthZ (authorization) “What are you allowed to do?” — enforce permissions. May this caller create an order? Refund? Read PII?

A JWT is mainly an AuthN badge (signed proof of who issued the token and for whom), that also carries AuthZ claims (scopes/roles) so each service can decide allow/deny without calling the IdP on every request.

What a JWT is (simple picture)

header.payload.signature

payload (claims) might include:
  sub   = who (user id or client/service id)
  iss   = who issued it (Keycloak / Cognito / Entra)
  aud   = who it is meant for (your API audience)
  exp   = when it expires (keep short-lived)
  scope = space-separated permissions  e.g. "orders.read orders.write"
  roles = coarse job titles             e.g. ["ROLE_ADMIN","ROLE_USER"]
  • The signature proves the IdP issued it and nobody tampered with the payload.
  • Services trust the JWT only after verifying signature + iss / aud / exp (and often nbf).
  • Never trust “they’re on our VPC / cluster network” alone — that is the opposite of zero-trust.

Scopes vs roles (the “rules” people put in JWTs)

ScopeRole
Meaning A specific permission to call an API capability. A job / group label that usually implies a bundle of permissions.
Typical shape orders.read, payments.refund, inventory.write ROLE_CUSTOMER, ROLE_SUPPORT, ROLE_ADMIN
Good for Service-to-service / OAuth2 APIs (least privilege per client). Human users and coarse UI/API gates (“admins can do X”).
Rule of thumb Ask: “Does this token grant this action?” Ask: “Is this principal in this group?”
Least privilege: give a client only the scopes it needs (e.g. inventory service gets inventory.write, not payments.refund). Roles are broader — still map them to concrete checks in code/policy, don’t treat “ADMIN” as magic.

How AuthZ is enforced in practice

  1. Gateway / resource-server filter (coarse). Spring Cloud Gateway or each Spring Boot resource server validates the JWT, then requires a scope/role for a route (e.g. POST /orders needs SCOPE_orders.write).
  2. Method security (fine-grained). Inside the service: @PreAuthorize("hasAuthority('SCOPE_orders.write')") or hasRole('ADMIN'), or SpEL that also checks “user may only see their order.” This is where “rules” meet business data.
  3. Optional OPA / policy sidecar. Instead of hard-coding every rule in Java, send “who + action + resource attributes” to Open Policy Agent (or similar). Policy as code (Rego) answers allow/deny — useful when rules change often or are shared across languages. 
Caller  →  mTLS (channel trust) + JWT (identity + scopes)
        →  Gateway checks JWT + route scopes
        →  OrderService @PreAuthorize / OPA
        →  allow or 401/403

Example “rules” you would actually state in an interview

  • Reject expired or wrong-aud tokens.
  • orders.write required to create an order; orders.read to fetch.
  • Service account for payment-service may call payments.charge, not users.admin.
  • User role CUSTOMER may read only orders where order.customerId == jwt.sub.
  • No JWT / invalid JWT → 401; valid JWT but missing scope/role → 403.
  • Deny by default: anything not explicitly allowed is forbidden.
One-liner: AuthN = prove identity (mTLS + short-lived JWT). AuthZ = enforce scopes/roles (and resource rules) at the gateway and in the method — never “they’re on our network, so they’re allowed.”
Describe how Hibernate manages database transactions. What potential issues can arise if transaction boundaries are not correctly defined in a multi-threaded web application, and how would you mitigate those issues?
HibernateTransactions
Answer (brief):
  • How: Session bound to a transaction (Spring @Transactional / JTA). Unit of work flushes/commits at boundary; LazyLoading works only while session is open.
  • Issues: Long transactions hold DB locks; session-per-thread misuse across threads; LazyInitializationException; dirty reads/lost updates; connecting multiple threads to one Session (not thread-safe).
  • Mitigate: Short service-layer transactions; one Session per request/thread; open-session-in-view only if deliberate; optimistic locking (@Version); never share Session across threads; clear tx boundaries for read vs write.

Note seen in chat input / message: @Transactional(Rollback=true) — is this valid?
Spring@Transactional
Answer (brief): Invalid / misleading. Correct attributes are e.g. @Transactional(rollbackFor = Exception.class) or @Transactional(noRollbackFor = …). Default already rolls back on unchecked exceptions; there is no Rollback=true attribute.

Distributed systems & cloud

Design a distributed system for real-time analytics on high-velocity data streams (e.g., IoT sensor data) that must remain available despite node failures. What key architectural choices would you make and why?
StreamingHAArchitecture
Answer (brief):
  • Ingest: Durable, partitioned log (Kafka / Kinesis / Pub/Sub) with replication factor ≥ 3.
  • Process: Stateless stream processors (Flink / Spark Structured Streaming / Kafka Streams) with checkpointing and exactly-once or at-least-once + idempotent sinks.
  • Storage: Hot path: time-series / OLAP (ClickHouse, Druid, Timestream); cold: object storage.
  • Availability: Multi-AZ; consumer group rebalance; no single coordinator SPOF; circuit breakers and backpressure.
  • Why: Decouple producers from consumers; scale partitions horizontally; survive broker/node loss without data loss.

Kubernetes & CI/CD

During a blue-green deployment in Kubernetes, how would you ensure zero downtime and safe rollback if issues are detected post-switch? Describe the necessary steps and configurations.
KubernetesBlue-Green
Answer (brief):
  • Run green Deployment alongside blue; both healthy via readiness/liveness probes.
  • Smoke-test green (Job, synthetic checks) before sending real users.
  • Cutover: Point Service selector / Ingress backend to green labels only when green is Ready.
  • Zero downtime: Keep blue pods until green is verified; connection draining / preStop hooks; session affinity awareness.
  • Rollback: Flip selector back to blue instantly; retain blue image/replicas until soak period ends; automate with Argo Rollouts / Flagger if preferred.

Blue vs green in plain English

Think of two complete copies of your app sitting in the cluster at once. Only one copy is “live” (getting user traffic). The colors are just nicknames:

ColorPlain English
Blue The current live version users already use (old/stable).
Green The new version you just deployed and are warming up (not live yet, or about to become live).
After a successful switch, people often rename mentally: yesterday’s green becomes today’s blue (the new “current live”), and the next release starts as a fresh green again. The names are roles, not permanent labels on servers.

How traffic moves (the “switch”)

  1. Before: Users hit a stable entry point (Service / Ingress / load balancer). That entry point sends all traffic to blue pods.
  2. Deploy green: Start a second set of pods with the new image. Users still only see blue. Green is idle from a user perspective.
  3. Health-check green: Wait until green pods pass readiness (and your smoke tests). Blue still serves everyone.
  4. Flip: Change the Service (or Ingress) so it now points at green instead of blue. New requests go to green. That flip is the cutover.
  5. Keep blue warm: Do not delete blue yet. If green misbehaves, flip the Service back to blue = instant rollback.
  6. Later: After a soak period, tear down blue to save cost.
Users / browser
       │
       ▼
  Ingress / Load balancer   (stable hostname: api.example.com)
       │
       ▼
  Service  (selector = which pods get traffic)
       │
       ├──► BLUE pods  (v1, live)     ◄── traffic BEFORE switch
       └──► GREEN pods (v2, standby)  ◄── traffic AFTER switch

Zero downtime means: green is fully ready before you flip; blue stays up during the flip; in-flight requests on blue can finish (graceful shutdown / preStop / connection draining).

What you actually use in Kubernetes (not a special “blue-green console”)

There is no separate product called “Blue-Green Console.” You do this with normal Kubernetes objects and the usual tools:

PieceRole in blue-green
Deployment (×2) One Deployment (or ReplicaSet) for blue pods, one for green pods — different labels/images.
Service Stable ClusterIP / name. You change its selector labels from version=blue to version=green to flip traffic.
Ingress (optional) External HTTP entry. Can point at one Service, or at two Services if you stage traffic.
Probes readinessProbe / livenessProbe so green only receives traffic when healthy.
kubectl / CI CLI (or GitLab/Jenkins/Argo job) applies YAML: create green, wait ready, patch Service selector, optionally delete blue.
Optional UI Kubernetes Dashboard, Lens, OpenShift Console, cloud consoles (EKS/AKS/GKE) — only viewers; the switch is still Deployment + Service.
Optional controllers Argo Rollouts / Flagger / Spinnaker can automate the flip and metrics checks for you. 
# Example idea (labels):
# Blue Deployment:  app=shop, color=blue,  version=v1
# Green Deployment: app=shop, color=green, version=v2
#
# Live Service initially:
#   selector: { app: shop, color: blue }
#
# Cutover (kubectl / CI):
#   kubectl patch svc shop -p '{"spec":{"selector":{"app":"shop","color":"green"}}}'
#
# Rollback:
#   patch selector back to color=blue
Interview tip: Say clearly that blue-green is a traffic-routing pattern on top of Kubernetes Deployments + Service (and maybe Ingress). You are not replacing Kubernetes with a different platform — you are using two pod sets and flipping which set the Service selects.

What is a canary deployment? (plain English)

A canary is like sending a small flock of birds into the mine first. You release the new version to a small percentage of users (or one pod / one region), watch errors and latency, then gradually increase traffic — or abort and send everyone back to the old version.

Blue-greenCanary
How traffic moves All-or-nothing flip (100% blue → 100% green) Gradual (e.g. 5% → 25% → 50% → 100% new)
Risk Lower if you tested green well; but one bad flip hits everyone at once Limits blast radius — only a slice of users sees the new build first
Rollback Flip Service back to blue Drop canary weight to 0% / scale canary pods to 0
Typical K8s tooling Two Deployments + one Service selector flip Two Deployments + weighted Ingress / Service mesh (Istio, Linkerd) / Flagger / Argo Rollouts
When to use Simple cutover, clear “go live” moment, easy mental model High traffic / high risk changes where you want live production proof first 
Canary sketch:

  Users ──► Ingress / mesh
               ├── 95% ──► stable pods (v1)
               └──  5% ──► canary pods (v2)   ← watch metrics
                            then raise % if healthy
  • Canary ≠ blue-green: canary shares traffic; blue-green usually keeps idle standby then flips fully.
  • Rolling update (default kubectl set image / Deployment strategy): Kubernetes replaces pods gradually inside one Deployment. Related idea, but not the same as a named canary with explicit % routing and analysis.
  • Smoke test: you hit green/canary yourself before users; canary lets real users hit a small slice.
One-liner for interviews: Blue-green = two full environments, switch 100% when ready. Canary = drip the new version to a few users first, then widen if metrics look good.
A team reports that their GitLab CI pipeline frequently stalls during artifact upload to a remote server. How would you diagnose and resolve this issue while ensuring minimal disruption to the deployment process?
GitLab CIArtifacts
Answer (brief):
  • Diagnose: Job logs + runner metrics; network path to artifact store (S3/MinIO/GitLab object storage); DNS/TLS timeouts; artifact size; concurrent upload limits; disk I/O on runner.
  • Resolve: Compress/exclude large paths; use cache vs artifacts appropriately; multipart uploads to S3 / increase timeouts; dedicated high-bandwidth runners; store large binaries in object storage and pass URLs, not full zip through GitLab artifacts.
  • Minimal disruption: Fix on a canary runner first; add retry with backoff on upload job; keep deploy jobs gated on successful upload checksum, not wall-clock hope.

Large file upload to S3 is failing — how to optimize without losing data

Common follow-up when CI artifacts (or any big binary) upload to S3/MinIO stalls or fails mid-transfer.

Do not keep retrying one giant single-PUT of a multi‑GB file. A network blip forces you to restart from byte 0, wastes time, and raises the chance you accept a truncated object if you are not careful about integrity checks.

Plain English: what goes wrong

  • One HTTP request carrying the whole file times out or drops → upload fails.
  • If a client “succeeds” without verifying size/checksum, you can store a corrupt or partial object.
  • CI then deploys or consumes that object → data loss / broken releases.

Optimize the upload (keep every byte)

  1. Multipart upload (main fix). Split the file into parts (e.g. 8–100 MB each). Upload parts in parallel. S3 only assembles the final object after all parts succeed (CreateMultipartUpload → UploadPart × N → CompleteMultipartUpload). Failed parts retry individually — you do not re-send the whole file.
  2. SDK / CLI that already does this. Prefer AWS CLI aws s3 cp / sync (multipart by default for large files), Transfer Manager in the AWS SDK, or aws s3api multipart calls — rather than a raw single PutObject in your own script.
  3. Retry only failed parts with exponential backoff + jitter. Keep the multipart upload ID; resume instead of aborting unless you are giving up.
  4. Tune part size and concurrency for the network: fewer huge parts on flaky links; more parallel parts on fat pipes — without flooding the runner’s NIC or hitting S3 request rate limits.
  5. Timeouts & idle limits: raise client read/write timeouts for large parts; avoid load balancers that cut long idle connections mid-upload.
  6. Optional: compress before upload (gzip/zstd) if the content compresses well — smaller transfer, same data after download+decompress. Do not compress already-compressed formats (zip, jpg, mp4) expecting big wins.
  7. Transfer Acceleration / closer region / VPC endpoint when latency or public-internet path is the bottleneck.

Guarantee you did not lose or corrupt data

CheckWhy it matters
Checksums (CRC32C / SHA-256 / MD5 where appropriate) Client and S3 agree each part (and the whole object) matches what you sent. AWS SDKs can enforce flexible checksums on upload.
Compare sizes Local file size == ContentLength / head-object size after upload.
ETag awareness For multipart objects, ETag is not a simple MD5 of the whole file — use explicit checksums or download+hash for final proof.
Complete only when all parts OK Never treat “some parts uploaded” as success. Incomplete multipart uploads are not the final object (and should be aborted/lifecycle-cleaned).
Idempotent key / versioning Upload to a temp key (or new version), verify, then copy/rename to the final key so consumers never see a half-written object.
Gate the next CI step Deploy/download only after verify job passes (checksum + head-object). 
# Sketch: large file with AWS CLI (multipart under the hood)
aws s3 cp huge-artifact.zip s3://my-bucket/artifacts/huge-artifact.zip \
  --expected-size $(stat -c%s huge-artifact.zip)   # where supported
# Then verify:
aws s3api head-object --bucket my-bucket --key artifacts/huge-artifact.zip
# Compare ContentLength to local size; optionally download to a scratch path and sha256sum
Interview one-liner: Use multipart upload so failures retry by part, then verify checksum/size (and only then publish the final key) so a flaky network never leaves you with a truncated file.

Compliance

A fintech company must comply with both PCI DSS and GDPR. Describe your approach to ensuring ongoing compliance with both standards, identifying areas where requirements might conflict or overlap, and how you would resolve these issues in practice.
PCI DSSGDPRFintech
Answer (brief):
  • Approach: Shared control framework (policies, encryption, access control, logging, IR); continuous evidence (config-as-code, SIEM, quarterly ASV / DPIA cadence); tokenize card data; minimize PII.
  • Overlap: Encryption, least privilege, audit trails, secure SDLC, incident response — implement once, map to both frameworks.
  • Tension: PCI wants retained logs/evidence; GDPR wants data minimization & erasure. Resolve by: short PII retention with justified legal basis; tokenize PAN outside GDPR subject-access where possible; erase personal data while retaining non-personal security logs; separate cardholder environment (CDE) from general CRM.
  • Practice: Privacy-by-design reviews, DPO + security liaison, vendor DPAs, regular gap assessments.
