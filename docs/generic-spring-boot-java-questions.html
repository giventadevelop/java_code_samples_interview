Nested @Transactional — single or multiple transactions?

Given OrderService.createOrder, PaymentService.processPayment, and InventoryService.updateStock each annotated with @Transactional (no propagation override): is this one transaction or multiple? What happens if payment fails?
Spring Boot @Transactional Propagation
Verdict: one (single) transaction — not three separate ones — when all methods use the default propagation Propagation.REQUIRED and calls go through Spring proxies (@Autowired beans, not this.).

Why it is a single transaction

  • Default propagation is REQUIRED: join an existing transaction if one is active; otherwise start a new one.
  • createOrder starts TX-1, then calls paymentService and inventoryService.
  • Those methods see TX-1 already active → they join TX-1. No new physical DB transaction is opened.
  • Seeing @Transactional on three methods does not mean three transactions.

Code under discussion

@Service
public class OrderService {
    @Autowired private PaymentService paymentService;
    @Autowired private InventoryService inventoryService;

    @Transactional
    public void createOrder(OrderRequest request) {
        Order order = new Order(request);
        orderRepository.save(order);
        paymentService.processPayment(order);   // joins same TX
        inventoryService.updateStock(order);    // joins same TX
    }
}

@Service
public class PaymentService {
    @Transactional
    public void processPayment(Order order) {
        Payment payment = new Payment(order);
        paymentRepository.save(payment);
        if (payment.isFailed()) {
            throw new PaymentException("Payment failed");
        }
    }
}

@Service
public class InventoryService {
    @Transactional
    public void updateStock(Order order) {
        Inventory inventory = inventoryRepository.findByProduct(order.getProductId());
        inventory.decrementStock(order.getQuantity());
        inventoryRepository.save(inventory);
    }
}

If payment throws

  • Runtime exception (or unchecked) marks the whole TX-1 for rollback.
  • Order save and payment save are rolled back together; inventory never runs (or also rolls back if it had).
  • Checked exceptions do not roll back by default unless rollbackFor is set.

When would it be multiple transactions?

ChangeResult
@Transactional(propagation = REQUIRES_NEW) on payment / inventory Separate nested transactions (suspend outer, commit/rollback independently)
NOT_SUPPORTED / NEVER Run without / forbid joining the outer TX
Self-invocation (this.processPayment() inside same class) Proxy skipped → inner @Transactional ignored (see self-invocation)
No outer @Transactional Each public proxied call that hits a transactional method can start its own TX
Interview one-liner: Three @Transactional methods with default REQUIRED on a call chain = one shared transaction. Use REQUIRES_NEW only when you intentionally want an independent commit (e.g. audit log that must survive outer rollback).

Spring Boot proxies — JDK Dynamic vs CGLIB

How does Spring Boot create proxy objects around beans, when does it do so, and what is the difference between JDK Dynamic Proxies and CGLIB?
Spring Boot AOP Proxy CGLIB

Spring Boot creates proxy objects using either JDK Dynamic Proxies or CGLIB proxies to wrap a target bean during application startup. The proxy intercepts method calls so Spring can inject cross-cutting behavior (transactions, security, caching, custom aspects) without changing your original source code.

The trigger mechanisms

During ApplicationContext initialization, Spring scans beans for indicators. If a bean matches any of the following, Spring may return a proxy instead of the raw instance:

  • AOP annotations: @Aspect, @Around, @Before, …
  • Declarative services: @Transactional, @Cacheable, @Secured, …
  • Scope mismatches: injecting a short-lived bean (prototype / request) into a long-lived singleton via @Scope(proxyMode = ScopedProxyMode.TARGET_CLASS) (or INTERFACES)

The two proxying technologies

Spring chooses based on the target class and configuration:

Feature JDK Dynamic Proxies CGLIB Proxies
Requirements Target must implement at least one interface No interface required
How it works Generates a runtime class that implements the same interfaces Generates a subclass of the target bean at runtime
Limitations Cannot proxy methods that are not on the interface Cannot proxy final classes or final / private methods
Spring Boot default Available if you prefer interface proxies Default in Spring Boot 2.x / 3.x, even when interfaces exist
Note: Core Spring Framework historically defaulted to JDK proxies when an interface was present. Spring Boot overrides that to prefer CGLIB so injecting the concrete class type does not blow up with a ClassCastException (JDK proxy is only the interface type, not the class).

Step-by-step lifecycle of proxy creation

This happens automatically inside the IoC container:

[BeanPostProcessor scans bean] ──► Matches @Transactional / @Aspect / … ?
         │                                       │
         ▼ (No)                                  ▼ (Yes)

                                                 │
                                                 ▼

                                      (JDK proxy or CGLIB)

  1. Instantiation: Spring creates the raw target bean.
  2. Post-processing: a BeanPostProcessor (e.g. AnnotationAwareAspectJAutoProxyCreator) intercepts it.
  3. Evaluation: processor checks pointcuts / proxy-triggering annotations.
  4. Configuration: on a match, Spring builds a ProxyFactory and attaches Advice (e.g. transaction interceptor).
  5. Generation & injection: the proxy is registered in the ApplicationContext instead of the raw bean for injection points.

The self-invocation pitfall

Proxies only intercept external calls through the injected bean. A local this.method() call goes straight to the real object and bypasses the proxy — so @Transactional, @Cacheable, etc. on that inner method do not run. 

@Service
public class MyService {

    public void publicMethod() {
        // Direct internal call — bypasses the proxy.
        // @Transactional on transactionalMethod WILL NOT APPLY!
        this.transactionalMethod();
    }

    @Transactional
    public void transactionalMethod() {
        // Database logic
    }
}
For @Transactional (and similar) to work, the call must come from outside the class through a Spring-injected reference so it routes through the proxy first. This is the same reason nested this.processPayment() in one class does not start a separate TX boundary.

How to fix self-invocation (quick options)

  • Split the bean: move transactionalMethod to another @Service and inject it (cleanest).
  • Self-inject: @Autowired MyService self; then self.transactionalMethod() (works with CGLIB; be careful with construction).
  • AopContext: (MyService) AopContext.currentProxy() (requires exposeProxy=true; less clean).
  • AspectJ weave mode: load-time / compile-time weaving can advise internal calls — heavier setup, rarely needed.
Interview one-liner: Spring wraps beans in JDK or (by default in Boot) CGLIB proxies via BeanPostProcessor so AOP advice can run. Self-invocation (this.) skips the proxy — call through an injected bean instead.
