1. Thread pools / cached thread pools — infinite tasks or threads?

Question: With a thread pool or cached thread pool from ExecutorService, is it possible to have an infinite number of tasks or threads created, or is there a limitation?
Short answer: You can submit a very large number of tasks, but threads are never truly infinite. Limits depend on the pool type. A cached thread pool has no configured max thread count and can grow until the JVM/OS runs out of resources.

Cached thread pool — Executors.newCachedThreadPool()

  • Tasks: you can submit a very large number of tasks (limited by memory and how work is accepted, not by a fixed task cap).
  • Threads: the pool can grow without a fixed upper bound. Idle threads are reused and typically die after 60 seconds of idle time. If work keeps arriving faster than threads finish, new threads keep being created.
  • So it is not truly infinite, but there is no configured maximum pool size.

Practical limits still apply:

  • OS / JVM maximum threads
  • Memory (each thread has a stack; often ~1MB by default)
  • CPU time wasted on context switching
Under heavy load, a cached pool can create so many threads that the JVM or machine becomes unstable. Prefer a bounded pool in production. 
ExecutorService cached = Executors.newCachedThreadPool();
// Creates threads as needed; idle threads reused; no maxPoolSize cap
cached.execute(() -> doWork());

Fixed / bounded pools (safer)

Pool Threads Tasks
newFixedThreadPool(n) Max n threads Unbounded queue → effectively unlimited queued tasks (memory risk)
newCachedThreadPool() Unbounded thread growth Tasks tend to run immediately; many threads under load
ThreadPoolExecutor with bounded queue + maxPoolSize Capped thread count Capped queue; then a rejection policy applies

Production recommendation

Prefer an explicit ThreadPoolExecutor with:

  • corePoolSize
  • maximumPoolSize
  • a bounded work queue
  • a rejection policy (AbortPolicy, CallerRunsPolicy, DiscardPolicy, or DiscardOldestPolicy
int cores = Runtime.getRuntime().availableProcessors();
ExecutorService pool = new ThreadPoolExecutor(
        cores,                 // corePoolSize
        cores * 2,             // maximumPoolSize
        60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),  // bounded queue
        new ThreadPoolExecutor.CallerRunsPolicy()
);

Interview one-liner

Cached pools can create unbounded threads; fixed pools cap threads but may queue unbounded tasks. True backpressure needs both a max pool size and a bounded queue (plus a rejection policy).

2. synchronized vs manual locking with ReentrantLock

Question: What does the synchronized keyword do, and how is it different from manually handling a lock object with ReentrantLock (lock() / unlock() and related methods?
Short answer: synchronized is a built-in language feature: the JVM acquires and releases the monitor for you (even if an exception is thrown). ReentrantLock is an explicit API lock from java.util.concurrent.locks — you call lock() / unlock() yourself (usually in try/finally) and get extra features that synchronized does not provide.

What synchronized does

synchronized uses an object’s intrinsic monitor lock (sometimes called a mutex). Only one thread at a time can hold that monitor for a given object (or class, for static synchronized methods).

  • Synchronized method: locks on this (instance) or the Class object (static).
  • Synchronized block: locks on whatever object you name (prefer a private final lock object).
  • Entry acquires the lock; exit (normal or exceptional) releases it automatically.
  • It is reentrant: the same thread can enter another synchronized method/block on the same monitor without deadlocking itself.
  • Waiting/signaling uses wait(), notify(), notifyAll() on the same monitor object.
private final Object lock = new Object();
private int count;

public void increment() {
    synchronized (lock) {   // JVM acquires lock
        count++;
    }                       // JVM releases lock automatically
}

What ReentrantLock is

ReentrantLock is a separate lock object you create and manage in code. It is also reentrant (same thread can lock multiple times and must unlock the same number of times), but acquisition/release is manual. 

private final ReentrantLock lock = new ReentrantLock();
private int count;

public void increment() {
    lock.lock();                 // you acquire
    try {
        count++;
    } finally {
        lock.unlock();           // you must release — always in finally
    }
}
Forgetting unlock() (especially when an exception is thrown) leaves the lock held forever for other threads. That is the main foot-gun versus synchronized, which always releases on block exit.

Core differences

Feature synchronized ReentrantLock
How you use it Language keyword / block API methods on a lock object
Lock release Automatic at end of block/method Manual unlock() (use try/finally)
Try without blocking Not available tryLock()
Timed wait for lock Not available tryLock(timeout, unit)

Fairness option Not configurable (JVM scheduling) new ReentrantLock(true) for fair FIFO-ish ordering
Multiple wait conditions One wait-set per monitor (wait/notify) Multiple Condition objects via newCondition()

Typical style Simpler, less error-prone for basic mutual exclusion More flexible when you need timeouts, try-lock, fairness, conditions

Important ReentrantLock methods

Method What it does
lock() Acquire the lock; wait indefinitely if held by another thread
lockInterruptibly() Like lock(), but can be interrupted while waiting
tryLock() Acquire immediately if free; otherwise return false (no wait)
tryLock(time, unit) Wait up to a timeout, then give up

ReentrantLock lock = new ReentrantLock();

if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {
    try {
        // critical section
    } finally {
        lock.unlock();
    }
} else {
    // could not get the lock in time — do something else
}

When to prefer which

  • Prefer synchronized for simple mutual exclusion: short critical sections, no need for timeout/try-lock/fairness. Less code, automatic unlock, harder to misuse.
  • Prefer ReentrantLock when you need:
    • try-lock / timed lock (avoid indefinite blocking)
    • interruptible acquisition
    • fair locking
    • multiple condition queues (producer/consumer with separate wait sets)
    • lock hand-off patterns that do not fit a single synchronized block structure
Note: Both are reentrant. “Reentrant” means the same thread can acquire the same lock again (for example method A synchronized calls method B synchronized on the same object). It does not mean different threads can enter at the same time.

Interview one-liner

synchronized = automatic intrinsic monitor lock. ReentrantLock = explicit lock API with lock/unlock, tryLock, timeouts, fairness, and Condition — more power, more responsibility to unlock in finally.

3. CompletableFuture and asynchronous processing

Question: What is CompletableFuture, and how do you use it for asynchronous processing in Java interviews?
Short answer: CompletableFuture is a Java 8+ implementation of Future that supports non-blocking callbacks, chaining, combining multiple async tasks, and explicit completion. Prefer it over raw Future.get() blocking when you need pipeline-style async work.

Interview bullet points

  • What it is: a promise-like result that may complete later with a value or an exception; you can attach callbacks instead of blocking a thread.
  • Start async work: CompletableFuture.supplyAsync(() -> fetch()) (returns a value) or runAsync(() -> sideEffect()) (no return value). Default executor is ForkJoinPool.commonPool(); pass a custom Executor for production control.
  • Chain (thenApply / thenCompose): thenApply transforms the result (like map); thenCompose flattens another CompletableFuture (like flatMap) — use compose when the next step is itself async.
  • Side effects: thenAccept consumes the result; thenRun runs when done without using the value.
  • Combine independent tasks: thenCombine(other, (a, b) -> merge) waits for both; allOf(cf1, cf2, …) waits for all; anyOf(...) completes when the first finishes.
  • Error handling: exceptionally, handle, or whenComplete — recover or log without burying checked exceptions in caller stacks.
  • Async vs sync stages: thenApply runs on the completing thread (or caller); thenApplyAsync schedules on an executor — important so you do not block I/O threads with heavy CPU work.
  • Timeouts (Java 9+): orTimeout / completeOnTimeout to fail or fall back if work runs too long.
  • vs Future: classic Future is mostly “submit and block on get”; CompletableFuture supports composition and non-blocking pipelines.
  • vs reactive (WebFlux / RxJava): CF is great for a handful of async calls; streams of many events usually fit reactive APIs better.
  • Pitfalls: forgetting a custom executor; calling blocking get()/join() on request threads; swallowing exceptions; creating unbounded work on commonPool().
ExecutorService pool = Executors.newFixedThreadPool(8);

CompletableFuture<User> user =
        CompletableFuture.supplyAsync(() -> userClient.get(id), pool);
CompletableFuture<Orders> orders =
        CompletableFuture.supplyAsync(() -> orderClient.list(id), pool);

CompletableFuture<Dashboard> dashboard = user.thenCombine(orders,
        (u, o) -> new Dashboard(u, o));

Dashboard result = dashboard
        .orTimeout(2, TimeUnit.SECONDS)
        .exceptionally(ex -> Dashboard.empty())
        .join(); // join = unchecked; prefer at the edge, not deep in library code
Interview one-liner: Use supplyAsync + thenCompose/thenCombine/allOf for async pipelines; always name your executor in production and handle failures with exceptionally/handle.

4. AWS CloudFormation vs Terraform

Question: What is the difference between AWS CloudFormation and Terraform? When would you choose each?
Short answer: Both are Infrastructure as Code (IaC). CloudFormation is AWS-native JSON/YAML (or CDK) tightly integrated with AWS. Terraform is HashiCorp’s multi-cloud tool (HCL) with a large provider ecosystem. Choose CFN for deep AWS-only stacks; Terraform when you need multi-cloud, multi-vendor, or a single workflow across AWS + others.

Interview bullet points

  • CloudFormation: AWS service; templates declare resources; AWS manages create/update/delete as a stack; free to use (pay for resources).
  • Terraform: open-source / Terraform Cloud; providers for AWS, Azure, GCP, SaaS (Datadog, GitHub, etc.); state file tracks real-world resources.
  • Language: CFN = YAML/JSON (or CDK in TypeScript/Java/Python); Terraform = HCL (or CDKTF).
  • State: CFN state lives in AWS (stack events/resources); Terraform uses a state file (local or remote backend like S3 + DynamoDB lock) — state security and locking are interview hot topics.
  • Drift: both can detect drift; CFN has drift detection on stacks; Terraform plan compares config to state/reality.
  • Modules / reuse: Terraform modules are a first-class strength; CFN has nested stacks / modules; CDK improves reuse for CFN users.
  • Rollbacks: CFN stack updates can roll back automatically on failure; Terraform applies are more “forward”; you design careful plans and sometimes targeted destroys/recreates.
  • New AWS features: CFN often gets official support quickly as an AWS product; Terraform AWS provider may lag slightly until the provider updates.
  • IAM / security: both need least-privilege deploy roles; Terraform state can contain secrets — encrypt and lock remote state.
  • Team fit: all-in on AWS + org standards around stacks → CFN/CDK; platform team managing AWS + Cloudflare + Datadog + k8s → Terraform is common.
Topic CloudFormation Terraform
Cloud scope AWS only (native) Multi-cloud / multi-provider
Config language YAML / JSON / CDK HCL / CDKTF
State Managed by AWS stacks State file + backends / locking
Change preview Change sets terraform plan
Best when Deep AWS integration, StackSets, Guard/Control Tower Mixed vendors, reusable modules, one IaC tool
Interview one-liner: CloudFormation = AWS-native stacks; Terraform = multi-cloud IaC with explicit state. Same goal (declarative infra), different ecosystem and operational model.

5. Garbage collection — advanced features & interview Q&A

Question: What should you know about Java garbage collection for senior interviews — heap layout, collectors, pauses, and how you would tune or diagnose GC?
Short answer: GC automatically reclaims unreachable objects. Modern JVMs use generational (and sometimes regional) heaps with collectors like G1 (default in recent JDKs), ZGC, and Shenandoah aimed at low pause times. Interviews expect heap regions, stop-the-world vs concurrent work, and how you read GC logs / metrics.

Advanced GC feature bullets

  • Generational hypothesis: most objects die young → young gen (Eden + Survivor) collected often and cheaply; long-lived objects promote to old gen.
  • Minor vs major / full GC: young collections are frequent; old-gen / full collections are rarer and historically more expensive (STW).
  • Stop-the-world (STW) vs concurrent: STW pauses all app threads; concurrent collectors do marking/relocation alongside mutators to shrink pauses.
  • G1 GC (Garbage-First): heap split into equal-sized regions; prioritizes regions with most garbage; soft real-time pause goal via -XX:MaxGCPauseMillis; default on many modern JDKs.
  • ZGC / Shenandoah: ultra-low-pause collectors (often sub-ms to low-ms class goals) using colored pointers / concurrent compaction — strong for large heaps and latency-sensitive services.
  • Parallel / Throughput collectors: maximize throughput with parallel STW workers; less ideal when tail latency matters.
  • CMS (historical): concurrent mark-sweep for old gen; deprecated/removed in newer JDKs — know it for legacy apps, prefer G1/ZGC now.
  • Humongous objects (G1): objects larger than ~½ region size use contiguous humongous regions; can cause fragmentation / more frequent full GCs if abused.
  • String deduplication / compressed oops: memory-footprint optimizations (flags vary by JDK) that interviewers may mention for large heaps.
  • GC roots: stack locals, static fields, JNI refs, etc. — anything reachable from roots is live.
  • Soft / weak / phantom references: soft ≈ caches; weak ≈ canonical maps; phantom ≈ post-mortem cleanup / cleaner patterns (prefer Cleaner over finalizers).
  • Escape analysis / TLAB / allocation: JVM may scalar-replace or stack-allocate short-lived objects; thread-local allocation buffers speed young alloc.
  • GC logging & observability: unified logging (-Xlog:gc*), JFR, GC metrics in APM — diagnose pause spikes, allocation rate, promotion failures, heap fragmentation.
  • Tuning levers: heap size (-Xms/-Xmx), pause goals, region size, concurrent threads; fix allocation churn / leaks before “random flag tweaking.”

Common interview questions (with crisp answers)

How does the JVM know an object can be collected?
If it is not reachable from GC roots through any reference chain (ignoring special reference types’ semantics), it is eligible for collection.
Young vs old generation — why split the heap?
Most objects die quickly. Collecting a small young space often is cheaper than scanning the whole heap every time; survivors promote to old gen.
G1 vs ZGC — when would you pick each?
G1: solid default for many server apps; balance of throughput and predictable pauses. ZGC/Shenandoah: when you need very low latency on large heaps and can run a supported JDK build.
What causes frequent full GCs or long pauses?
High allocation rate, memory leaks / retained caches, heap too small, promotion failure, fragmentation (incl. humongous allocations), finalizer/cleaner backlogs, or wrong collector for the latency SLO.
Does System.gc() force a full collection?
It only suggests a GC (unless disabled via flags). Relying on it in production is a smell; prefer fixing allocation patterns and sizing.
How do you investigate a suspected memory leak?
Watch old-gen occupancy trend up across GCs; take a heap dump (jcmd / jmap / container tooling); analyze retained Dominator trees (MAT / VisualVM); check caches, ThreadLocals, listeners, static maps.
WeakHashMap vs a normal HashMap for a cache?
WeakHashMap uses weak keys — entries can disappear after GC when keys are otherwise unreachable. Useful for canonical mappings; for size-bounded caches prefer explicit policies (Caffeine / Guava) over hoping GC cleans up SoftReferences.
Collector Focus Interview note
Serial Single-threaded STW Small heaps / client / containers with tiny CPU
Parallel Throughput Batch jobs; longer pauses OK
G1 Balanced / region-based Common server default; pause-goal oriented
ZGC / Shenandoah Ultra-low latency Large heaps, latency SLOs
Interview one-liner: Explain reachability + generations, name G1 as the usual default, know ZGC for low-pause large heaps, and diagnose with allocation rate, GC logs, and heap dumps — not random -XX flags first.

6. GC differences: Java 8 vs Java 17

Question: What changed in garbage collection between Java 8 and Java 17?
Short answer: Java 8’s common server default was the Parallel collector (throughput-oriented). By Java 9+ G1 became the default, and Java 17 keeps G1 as the mainstream default while offering production-ready ZGC / Shenandoah for low latency. CMS was deprecated and later removed; GC logging moved to unified -Xlog.

Bullet points interviewers expect

  • Default collector: Java 8 server-class JVMs typically defaulted to Parallel GC; Java 17 defaults to G1 (G1 became default in JDK 9).
  • CMS: Concurrent Mark Sweep was still used on many Java 8 apps for lower old-gen pauses; it was deprecated in JDK 9 and removed in JDK 14 — Java 17 has no CMS; migrate to G1/ZGC/Shenandoah.
  • G1 maturity: G1 in Java 8 existed but was less often the default; by Java 17 it is the standard balanced collector with better pause targeting and region-based collection.
  • Low-pause collectors: ZGC and Shenandoah went from experimental / early-access style availability toward production options by Java 17 (exact “production” status landed across JDK 15–17 timeframe depending on collector).
  • GC logging: Java 8 often used PrintGC* flags (-XX:+PrintGCDetails, etc.). Java 17 uses unified JVM logging (-Xlog:gc*) — old PrintGC flags are obsolete.
  • Ergonomics / containers: Java 17 (and later 8u updates) better respect container CPU/memory limits; Java 8 era apps often mis-sized heaps inside Docker unless patched/flags were set.
  • Removed / niche: legacy combinations and some old flags disappear; prefer modern documented options for G1 pause goals and heap sizing.
  • Practical migration tip: when moving 8 → 17, re-baseline heap size, switch logging to -Xlog:gc*, drop CMS flags, validate pause/throughput with G1 first, then evaluate ZGC if latency SLOs demand it.
Topic Java 8 (typical) Java 17 (typical)
Default (server) Parallel GC G1 GC
CMS Common low-pause choice Gone — use G1 / ZGC / Shenandoah
Ultra-low pause Limited / experimental ZGC / Shenandoah viable
GC logs PrintGC* style flags -Xlog:gc* unified logging
Interview one-liner: Java 8 ≈ Parallel default + CMS era; Java 17 ≈ G1 default, CMS removed, ZGC/Shenandoah for latency, unified GC logging.

7. How is an Auto Scaling Group configured in AWS?

Question: How do you configure an Auto Scaling Group (ASG) in AWS?
Short answer: An ASG keeps a desired count of EC2 instances healthy across AZs. You configure a launch template (AMI, instance type, security groups, userdata), choose subnets/AZs, set min/desired/max capacity, attach scaling policies and health checks (EC2 and/or ELB), and optionally hook it to a load balancer target group.

Configuration bullets

  • Launch template / launch configuration: AMI, instance type, key pair, IAM instance profile, security groups, user data, EBS mapping. Prefer launch templates (launch configs are legacy).
  • VPC & subnets: place the ASG in multiple AZs for HA (e.g. private app subnets behind an ALB).
  • Capacity: MinSize, DesiredCapacity, MaxSize — ASG maintains desired; scales between min and max.
  • Health checks: EC2 status checks and/or ELB/ALB target-group health — unhealthy instances are replaced.
  • Load balancer integration: register with ALB/NLB target groups so traffic follows healthy instances.
  • Scaling policies:
    • Target tracking (e.g. keep CPU ~50% or ALB requests/target)
    • Step scaling / simple scaling on CloudWatch alarms
    • Scheduled scaling (business hours)
    • Predictive scaling (optional)
  • Cooldown protection: instance scale-in protection for long jobs / sticky critical nodes.
  • Lifecycle hooks: pause terminate/launch to drain connections or bootstrap (e.g. deregister from ALB, flush queues).
  • Mixed instances / Spot: On-Demand + Spot pools for cost; define instance-type overrides in the launch template / mixed instances policy.
  • IaC: define ASG in CloudFormation or Terraform (aws_autoscaling_group) with attached policies and alarms.
  • Cool-downs / warmup: avoid flapping; use warmup so new instances are not counted for metrics until ready.
Interview tip: ASG scales EC2 capacity. For containers you often use ECS capacity providers / EKS node groups (still ASG underneath for EC2), or serverless (Fargate/Lambda) instead of managing ASG directly.
Interview one-liner: Launch template + multi-AZ subnets + min/desired/max + health checks + scaling policy (usually target tracking on CPU or ALB request count), optionally behind an ALB.

8. Database indexes — benefits and drawbacks

Question: What are the benefits of using indexes, and what are the drawbacks?
Short answer: Indexes speed up reads/lookups/joins/sorts by avoiding full table scans, but they cost extra storage and slow writes (INSERT/UPDATE/DELETE must maintain every index). Index selectively on high-selectivity filter/join columns used by real queries.

Benefits

  • Faster SELECTs: locate rows by key without scanning the whole table.
  • Faster JOINs: nested-loop / merge joins use indexes on join keys.
  • Faster ORDER BY / GROUP BY: covering or ordered indexes can avoid sorts.
  • Uniqueness enforcement: UNIQUE / PRIMARY KEY indexes guarantee integrity.
  • Covering indexes: if all needed columns are in the index, the engine may skip the heap/table lookup (index-only scan).
  • Range queries: B-tree indexes help BETWEEN, </>, prefix LIKE 'abc%'.

Drawbacks

  • Write overhead: every insert/update/delete may update multiple indexes.
  • Storage cost: indexes consume disk (and buffer pool / cache memory).
  • Slower bulk loads: loading with many indexes is expensive (sometimes drop/rebuild around ETL).
  • Wrong indexes hurt: low-selectivity columns (e.g. boolean flags) may not help and can mislead the planner.
  • Maintenance: fragmentation, bloat (Postgres), statistics must stay fresh.
  • Locking / contention: hot index pages can become concurrency bottlenecks.
  • Over-indexing: too many indexes → worse write latency and little read gain.
Good candidates Often poor candidates
PK/FK, join keys, frequent WHERE filters, high cardinality Rarely filtered columns, very low cardinality alone, wide rarely used composites
Interview one-liner: Indexes trade write cost and disk for read speed — index what your queries actually filter/join on; measure with EXPLAIN before adding more.

9. Idempotency — what it is and which CRUD ops support it

Question: What is idempotency, and which CRUD operations are idempotent?
Short answer: An operation is idempotent if calling it once or many times with the same request leaves the system in the same final state (side-effect-wise). Retries are safe. In CRUD/HTTP terms: GET, PUT, and DELETE are typically idempotent; POST (Create) usually is not unless you design it that way (e.g. idempotency keys).

What “idempotent” means

  • Repeating the call does not keep applying extra effects (f(x) = f(f(x)) for the resource state).
  • Responses may differ slightly (e.g. DELETE second time → 404), but the resource state stays consistent with a single successful apply.
  • Critical for retries, at-least-once messaging, flaky networks, and payment APIs.

CRUD / HTTP mapping

CRUD Typical HTTP Idempotent? Why
Read GET / HEAD Yes No state change; reading twice is the same as reading once
Update (replace) PUT Yes (when it replaces full state) Sending the same representation again leaves the resource identical
Delete DELETE Yes After first delete, resource is gone; further deletes do not delete “more”
Create POST No (by default) Each call may create another resource / charge / row
Partial update PATCH Often no (not guaranteed) Depends on semantics (e.g. “increment counter” is not idempotent; “set field=X” can be)

Interview bullets

  • Safe vs idempotent: Safe methods (GET) have no side effects. Idempotent methods may have side effects, but repeats do not change the outcome beyond the first apply (PUT/DELETE).
  • Make POST idempotent: client sends an Idempotency-Key; server stores key → response and returns the same result on retry instead of creating a duplicate.
  • PUT vs POST: PUT to a known URI (/orders/123) is naturally idempotent; POST to /orders that auto-generates IDs is not.
  • Messaging: consumers should be idempotent (dedupe by message id) because brokers often deliver at-least-once.
  • DB angle: UPDATE ... SET status='PAID' WHERE id=? is idempotent; UPDATE ... SET balance = balance + 10 is not.
Nuance: HTTP specs treat GET/PUT/DELETE as idempotent by contract. Your implementation must honor that — a buggy DELETE that decrements a counter twice is still “wrong,” even if the verb is usually idempotent.
Interview one-liner: Idempotent = safe to retry. CRUD: Read/Update(replace)/Delete yes; Create (POST) no unless you add idempotency keys or a deterministic resource id.

10. Angular — REST timeout & preventing double API submit

Question: How do you set a timeout on an Angular REST (HttpClient) call? And which Angular/RxJS feature helps prevent double submission of an API request?
Short answers:
  • Timeout: use RxJS timeout({ first: ms }) (or legacy timeout(ms)) on the HttpClient observable (globally via an interceptor if needed).
  • Double submit: use exhaustMap (ignores new clicks while the request is in flight) and/or disable the submit button with a submitting flag. switchMap cancels the previous call instead of ignoring — different semantics.

REST API timeout in Angular

  • Per-request: pipe timeout after http.get/post.
  • Global: HTTP interceptor that applies timeout to every outgoing request (optional per-URL overrides).
  • On timeout: observable errors with TimeoutError; handle in catchError / UI toast.
  • Related: backend/gateway timeouts still matter; client timeout only aborts the browser wait / unsubscribes the request.
import { timeout, catchError } from 'rxjs/operators';
import { TimeoutError, throwError } from 'rxjs';

this.http.post('/api/orders', body).pipe(
  timeout({ first: 10_000 }), // fail if no response in 10s
  catchError(err => {
    if (err instanceof TimeoutError) {
      return throwError(() => new Error('Request timed out'));
    }
    return throwError(() => err);
  })
).subscribe(...);

Preventing double submission of an API request

  • exhaustMap (best RxJS answer): while an inner HTTP call is active, new trigger emissions (button clicks) are ignored. Ideal for “Submit” to avoid duplicate POSTs.
  • UI disable flag: set submitting = true on click; bind [disabled]="submitting"; clear in finalize(). Simple and interview-friendly.
  • switchMap: cancels the previous in-flight request when a new one starts — good for search-as-you-type, not always right for create/submit (may cancel a valid POST).
  • concatMap: queues clicks one after another — can still fire multiple POSTs sequentially (usually not what you want for “pay now”).
  • debounceTime / throttleTime: reduces click spam but does not guarantee only one in-flight call by itself.
  • Form state: reactive forms + disable controls while pending; template ngForm submitted state alone is not enough for async APIs.
  • Server-side: still use idempotency keys for POST — UI guards can fail (double tab, retries).
// exhaustMap: ignore extra clicks until the HTTP call completes
submit$ = this.submitClick$.pipe(
  exhaustMap(() => this.http.post('/api/orders', this.form.value).pipe(
    finalize(() => this.submitting = false)
  ))
);

// Button pattern
onSubmit() {
  if (this.submitting) return;
  this.submitting = true;
  this.http.post('/api/orders', this.form.value)
    .pipe(finalize(() => this.submitting = false))
    .subscribe(...);
}
Operator / approach Double-submit effect Typical use
exhaustMap Ignores new triggers while in flight Form submit / “Buy” button
switchMap Cancels previous request Typeahead search
concatMap Runs all, one after another Ordered sequential jobs
[disabled] + flag Blocks UI re-entry Simple templates
Interview one-liner: Timeout with RxJS timeout on HttpClient; prevent double POST with exhaustMap and/or disable the button while submitting is true.

11. ExecutorService summary & modern thread features (Java 17 / 21)

Question: Give a brief summary of ExecutorService, and what is new for threading around Java 17 (and the follow-on LTS Java 21)?
Short answer: ExecutorService is the standard API to run tasks on a managed thread pool instead of creating raw Threads. Java 17 (LTS) still uses platform threads with the classic executors. Virtual threads (Project Loom) became a standard feature in Java 21 — often discussed together with “modern Java / Java 17+” interviews, but they are not part of JDK 17 itself.

ExecutorService — brief summary

  • What it is: an interface that accepts tasks (Runnable / Callable) and runs them asynchronously on pooled threads.
  • Why use it: reuse threads, bound concurrency, get Future/CompletableFuture results, orderly shutdown.
  • Common factories: newFixedThreadPool(n), newCachedThreadPool(), newSingleThreadExecutor(), newScheduledThreadPool(n), or a custom ThreadPoolExecutor.
  • Submit vs execute: execute = fire-and-forget; submit returns a Future.
  • Lifecycle: shutdown() (orderly) vs shutdownNow() (interrupt / drain); await termination with awaitTermination.
  • Best practice: prefer a bounded ThreadPoolExecutor (max threads + bounded queue + rejection policy) in production — see §1.
ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Integer> f = pool.submit(() -> compute());
Integer result = f.get();
pool.shutdown();

Threading around Java 17 (what is / isn’t new)

  • Java 17 LTS: still platform threads (1 OS thread ≈ 1 Java thread). No virtual threads in 17.
  • Same core model: Thread, ExecutorService, ForkJoinPool, CompletableFuture remain the daily toolkit.
  • Deprecations to know: legacy security-manager direction and some older APIs evolve across 17→21; prefer modern concurrency utilities over Thread.stop-era patterns (long obsolete).
  • Interview trap: do not claim “Java 17 introduced virtual threads.” Say: Java 17 is the LTS baseline; virtual threads arrived in Java 21.

New / major thread features after Java 17 (Java 21 — mention in “modern Java” answers)

  • Virtual threads (JEP 444, Java 21): lightweight threads managed by the JVM; millions can exist because they unmount from OS carriers when blocking on I/O. Ideal for high-concurrency servers (many blocking JDBC/HTTP calls).
  • Create them: Thread.ofVirtual().start(runnable) or Executors.newVirtualThreadPerTaskExecutor().
  • With ExecutorService: virtual-thread-per-task executor still implements ExecutorService — same submit API, different thread type.
  • Structured concurrency (preview in 21): StructuredTaskScope treats related tasks as a unit (cancel together, clearer failure handling) — contrast with ad-hoc CompletableFuture.allOf.
  • When virtual threads help: lots of blocking I/O, simple thread-per-request style. When they don’t magically help: heavy CPU-bound work (still limited by cores); avoid pinning (long synchronized / native frames) where possible.
  • Migration note: many apps on Java 17 stay on platform-thread pools; upgrading to 21 lets you adopt virtual threads without rewriting business logic if code already uses executors / blocking APIs cleanly.
// Java 21 — virtual thread per task
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> f = executor.submit(() -> httpClient.get(url));
    System.out.println(f.get());
}
