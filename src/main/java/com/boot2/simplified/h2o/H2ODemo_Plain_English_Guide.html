1. Big picture — what is this demo?

Imagine you want to make water: you need 2 Hydrogen (H) and 1 Oxygen (O). Many atoms arrive at once. The computer must not let three Hydrogens go through alone.

  • H2ODemo.java — starts one thread per atom from a string like HOH.
  • H2O.java — the reaction room rules (tickets + waiting for partners).
Tip: H2ODemo only creates threads and calls h2o.hydrogen(...) or h2o.oxygen(...). The hard concurrency rules live in H2O.java.
2. Runnable vs Thread — can you call run()?

What is a Runnable?

A Runnable is just a small job: “here is work to do.” It has one method: run().

In this demo you see two kinds of Runnable jobs:

  1. The atom job passed into new Thread(() -> { ... }) — that lambda is a Runnable. It calls hydrogen or oxygen.
  2. The print job () -> System.out.print("H") passed into hydrogen(...) — also a Runnable. Inside H2O, after partners arrive, the code calls releaseHydrogen.run() to print H.
Important: Calling runnable.run() or thread.run() does NOT start a new thread. It runs the work on the same thread that called it — like a normal method call. To start parallel work you must call thread.start().
What you call What really happens Acts like a thread?
myRunnable.run() Runs the job now, on the current thread No
myThread.run() Same — still the current thread (bad if you wanted parallel) No
myThread.start() JVM creates a new thread, then that thread calls run() Yes
releaseHydrogen.run() inside H2O Just prints “H” on the atom’s worker thread (after barrier) No new thread — print only
In H2ODemo: we wrap each atom in new Thread(...) and call workers[i].start(). That is what makes atoms run at the same time.
Memory tip (copy) 
Runnable = the work.
Thread = a worker that can run that work in parallel.
run() = do the work now (same thread).
start() = hire a new worker thread, then it calls run().
3. H2ODemo.main — step by step

Step A — Read the atom feed

String feed = args.length > 0 ? args[0] : "HOH";

If you pass a string on the command line (like HOHHOH), use it. Otherwise use default HOH (2 H + 1 O = one water).

Step B — Create one shared H2O controller

H2O h2o = new H2O();

One shared “reaction room” for all atoms. Inside it: 2 H tickets, 1 O ticket, and a barrier that waits for 3 atoms.

Step C — Make one Thread per letter

Thread[] workers = new Thread[feed.length()];
// for each char: new Thread(() -> h2o.hydrogen(...) or h2o.oxygen(...), "H-0")

Plain English:

  • Letter H → thread named H-0, H-1, … that calls h2o.hydrogen(() -> System.out.print("H"))
  • Letter O → thread that calls h2o.oxygen(() -> System.out.print("O"))

The lambda () -> System.out.print("H") is a Runnable. It does not run yet. It runs later when H2O calls .run() after the barrier opens.

Step D — Start every thread

workers[i].start();

This is the real “go parallel” call. Each atom thread begins and tries to enter the reaction room through hydrogen / oxygen.

Step E — Wait until all atoms finish

for (Thread t : workers) {
    t.join();
}

join() means: “main thread, wait here until that worker is done.” So we do not print the final message too early.

4. Semaphore and CyclicBarrier in H2O (plain English)

Semaphore = tickets / door slots

In this class:

  • hSem = new Semaphore(2) — only 2 Hydrogen tickets
  • oSem = new Semaphore(1) — only 1 Oxygen ticket
  • acquire() — take a ticket (wait if none left)
  • release() — give the ticket back

Without tickets, 100 Hydrogens could all rush into the barrier and leave Oxygen out. Tickets enforce chemistry: at most 2 H and 1 O waiting for a molecule.

CyclicBarrier = “wait for the full team”

In this class:

  • barrier = new CyclicBarrier(3) — need 3 arrivals (2H + 1O)
  • await() — sit and wait until the 3rd friend arrives
  • When the 3rd arrives, all 3 wake up together, then the barrier resets for the next molecule
Tool Simple job In H2O
Semaphore Limit how many can enter Max 2 H, max 1 O in the chamber
CyclicBarrier Wait until a group is complete Release only when 2H + 1O are ready
5. How Semaphore and CyclicBarrier connect

Inside hydrogen (Oxygen is the same idea):

  1. Ticket first — hSem.acquire() (may wait if 2 H already inside).
  2. Then partners — barrier.await() (may wait for the other H and the O).
  3. Then print — releaseHydrogen.run() (prints H; this is NOT starting a thread).
  4. Always return ticket — hSem.release() in finally.
Why both? Barrier alone could let three Hydrogens through (all call await). Semaphores force the mix to be 2H + 1O. Together: correct chemistry + release as a group.
Common mistake: Thinking releaseHydrogen.run() starts another thread. No — it only runs the print callback on the same worker thread that already passed the barrier.

Picture for feed HOH

  1. Main creates 3 threads and calls start() on each.
  2. Two H threads take H tickets; one O thread takes the O ticket.
  3. All three call await() and wait for each other.
  4. When all three are there, they print letters (order may be HOH, OHH, or HHO).
  5. Tickets are released; main join()s and finishes.
6. How to run

From the project root java_code_samples_interview:

Compile
Customize Parameters:
mvn -q -DskipTests compile
Windows Single-Line:
mvn -q -DskipTests compile
Run H2ODemo
Customize Parameters:
java -cp target/classes com.boot2.simplified.h2o.H2ODemo HOH
Windows Single-Line:
java -cp target/classes com.boot2.simplified.h2o.H2ODemo HOH
Valid output: letters for one molecule may appear as HOH, OHH, or HHO. That is OK. Invalid overall ratios are not.
Quick recap
  1. H2ODemo starts one Thread per atom with start().
  2. A Runnable is only the job. run() alone does not create a thread.
  3. Semaphore = limited tickets (2H, 1O).
  4. CyclicBarrier(3) = wait until the full set arrives, then print together.
  5. releaseHydrogen.run() only prints — it does not start another thread.
